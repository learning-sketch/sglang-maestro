## 1 / 8　适配成本

*约 85 秒（1:25）*

先把成本摆清楚。左边是模型侧的节奏：主流模型持续更新，结构与精度不断变化，社区从发布到跑通是按天算的。

右边是我们这一侧的工作，三件事都要反复做：接入，把模型从启动带到精度、性能达标；补齐，框架与算子的缺口逐项补上；复验，每改一次就要重新验证一遍。

这三件里最贵的不是算力，是第三件——重复判断。同样的问题换个模型再判一遍，经验沉不下来。

中间这句是要害：芯片竞争力取决于硬件能力、软件成熟度与模型覆盖度。硬件能力在流片那天就定型了，模型覆盖度每天都在被社区改写，所以适配效率直接决定硬件能力能不能及时发挥出来。

命题因此只有一个：要扩大模型覆盖，只能把单个模型的适配成本降下来，把重复的排查、评测与调优组织成可复用的 Agent 流程。后面七页回答这件事怎么做。

**被问到再说**

- 三个待填的数，口径是：人周按 bring-up 到精度与性能双达标统计；算子缺口按该模型新增或需要重写的算子实现计；复验轮次按一次完整的改—测—判算一轮。
- 未调优内核与最优实现相差一个数量级，这是适配不能跳过的原因，也是算子层那条线要解决的问题。

## 2 / 8　软件栈

*约 65 秒（1:05）*

这一页说清楚 Agent 站在软件栈的哪一层。

从下往上，芯片、运行时与驱动、编译器，这几层昆仑芯已经做好了，我们按原样使用、一行不改，所以合并成一条。

往上两层才是动手的地方，页面上框出来了。上面一框是框架层：SGLang 是主线，XInfer 是昆仑芯自己的推理框架，这一层做模型接入、服务验证和按实测调优，第 4、5 页展开。

下面一框是算子层：XCN_ATEN_OPS。这一层补齐算子缺口、生成与调优实现、再用真机验证收益，第 6 页展开。

实心的三个模块是 Agent 直接参与的，其余由昆仑芯或社区提供，我们只做对接。

**被问到再说**

- 为什么不动下面几层：编译器、运行时、驱动是昆仑芯的交付物，改了既不好升级也不好交接；Agent 只通过它们暴露的接口拿编译、运行、性能和理论上限。
- vLLM 与 FlashInfer 画在图上只是标清楚位置，当前投入都在 SGLang 这条线上。

## 3 / 8　两个 Agent 纵览

*约 110 秒（1:50）*

两个 Agent 先给一个全貌。左边 model-agent 工作在模型层，做模型接入、服务验证与性能调优；右边 xpugen 工作在算子层，面向 M100 生成算子实现并调优。

两边的结构是一样的：都是先确认精度正确，再确认收益，中间那三个方块就是各自的验收链路，写的都是通过条件。模型只负责提出方案，是否合格由固定验收与真机测量决定，不由模型自己解释。两边也都有一个不作判据的诊断步骤——model-agent 独立采 Trace，xpugen 用模拟器定位瓶颈。

真正的区别是加了底色的那一行，测量范围。model-agent 测的是整个模型、真实服务与固定评测集；xpugen 测的是单算子，多形状、对照独立参考。

中间两条箭头是交接。向右：由 Trace 定位到的瓶颈算子，转成算子层的输入规格与请求。向左：新内核回来，进入模型层的候选迭代，重新判一次。

最下面这句是整页的要点：同一个算子内核，既要通过算子验收，也要通过整模型复验。算子 bench 衡量的是局部收益，能不能交付由真实模型上的复测决定。第 7 页会用一个算例说明这两者能差多少。

**被问到再说**

- 两个 Agent 分属不同仓库，本页画的是职责与交接关系；交接目前走到哪一步——人工传递需求与内核，还是已有接口——按实际情况回答。
- 机制上算子层的产出可以直接作为模型层的候选：候选补丁允许的后缀里包含 .xpu，不需要额外的集成改造。
- 两层提速之间的落差取决于该算子在端到端耗时中的占比，第 7 页有算例。没有占比数据时，单算子的倍数不能外推为模型加速比。

## 4 / 8　模型层 · 执行迭代

*约 105 秒（1:45）*

这一页是模型层的工作方式：人定目标，Agent 在固定约束内迭代，结果交回人验收。

最上面一行是三个阶段：架构接入做新架构的逐层验收，性能调优在实测环境下迭代，持续优化按 Trace 长期迭代。今天重点是中间这条。

左边是人的第一段工作：确定模型、负载与并发，精度阈值与预算，已知缺陷对应的修复方案，以及输入与任务约定。这一步定完就冻结——契约改动之后，已有结果不再沿用。

中间整段无人值守。A 先完成预检再验收基线；B 独立采样 Trace，只用于诊断，不计入收益；C 是候选迭代，小步改动、逐轮验证收益，右边那个回环标注的就是它；D 最终复验，重测基线与候选，独立复验一遍。

右边是人的第二段工作：核对精度、性能与失败记录，通过就导出启动方案，失败或没有收益转人工诊断。每一轮都能追溯，必要时回退。

最下面这条回环是外循环：把验证过的规则、补丁与失败记录沉淀下来，供下一次任务复用。这正是第 1 页那个命题——让重复判断逐次减少。

**被问到再说**

- 预算与预留：总预算和最终复验预留都写在任务契约里。最终复验要对每个候选重跑一遍完整评测，预留偏小会导致 D 阶段做不完，建议按候选数量与实测单轮耗时自适应，而不是写死一个常数。
- 恢复运行不重置截止时间，所以临近结束被中断再恢复，D 阶段可能拿不到足额预留，必要时应显式延长并记入状态。
- 已验收的候选不会成为新基线，后续候选始终从基线分叉，因此多个独立收益不会叠加——一次运行交付的是其中最好的一个，而不是它们的组合。

## 5 / 8　模型层 · 候选验收

*约 100 秒（1:40）*

这一页放大上一页的 C 阶段：里面每一个候选，都要走完左边这条流水线。

先准备：在隔离副本上应用改动，构建并记录产物信息。服务启动时核对端口、设备与模型路径，确认被测的确实是这个候选。

然后三道条件，顺序按成本由低到高。第一道看输出有没有变，判据是贪心 token 完全一致；第二道看质量，正确率与解析率都不许降；第三道看是不是确实更快，收益要大于 3%、回归不超过 5%，重复压测取中位，还要大于噪声极差。任一道不过就停止后续测试，不再占用设备时间，但失败证据保留。

下面两条保证候选之间可比：输入、精度、上下文与缓存条件全部固定，prompt 的 token 数必须等于冻结值；诊断和正式压测分开，收益由关闭 profiler 的独立复测确认——不能靠减少实际工作量换速度。

右边放这条流水线判出来的结果。口径要强调：只有独立复验通过的收益才进入最终交付，筛选阶段看起来有收益、复验没过的，一个都不算。

**被问到再说**

- 质量这一道如果取零容差，在小筛选集上一道题就是几个百分点，而且与容许一定的数值漂移自相矛盾：漂移唯一的表现形式就是临界题翻转。更稳妥的做法是同一批题目上的配对检验。
- 重复三次取极差只能作为粗略估计，而且基线与候选分处不同时间段，设备漂移会直接进入对比。要让数字经得起追问，需要在同一窗口内交错测量 A / B / A。
- 第一道比较的是候选与 M100 基线，而不是参考实现，因此基线自身的数值错误发现不了。架构接入阶段已有冻结的独立参考，性能调优阶段应该在 A 阶段继承一次。

## 6 / 8　算子层 · 生成与迭代

*约 100 秒（1:40）*

这一页是算子层：xpugen 怎么写算子、怎么判算子。

左边写算子，是全流程唯一的模型。生成之前先澄清需求与约束、比较方案、固定输入语义，然后依据硬件说明卡生成实现，明确数据搬运、计算与同步。

右边判算子，是固定规则，这一侧没有模型。L0 编译与运行，L1 多形状多精度对照独立参考，Bench 在固定负载上真机计时，Profile 用模拟器定位瓶颈——注意 Profile 不作判据。评测结果与瓶颈证据原样回传，进入下一轮。

下面一行是架构要点：写与判都不碰硬件，与硬件耦合的只有后端这一层，编译、运行、性能采集。换新芯片只需补齐这一层。

右边是目前的实测样例，RMSNorm：固定 4096 乘 4096 的负载，相对基线加速 1.24 倍，741.2 微秒降到 595.6。最优版本重复测了两次，595.64 和 595.63，结果接近。这是单算子样例，还没有规模化统计，所以这里不报聚合指标。

**被问到再说**

- 1.24 倍的基线是哪一个实现，需要讲清楚：相对未调优实现、相对现有库实现、还是相对第 0 轮反推出来的规格，结论的分量完全不同。
- 最优版本只重复测了两次。两次接近说明没有明显抖动，但不足以支撑噪声水平的结论，被追问时按实际重复次数回答，不要说成已验证稳定。
- 轮数口径：精度收敛默认八轮；性能调优不设轮数上限，铁律是连续若干轮没有进展才允许下停滞结论。

## 7 / 8　局部加速到整体收益

*约 105 秒（1:45）*

上一页说算子快了不等于模型快了，这一页用一个算例说明能差多少。

先说清楚这是假设算例：固定总耗时 100 毫秒，其他部分不变，既不是模型实测，也不是 SLO 容量预测。

两个场景，区别只在算子占比。场景 A 偏 GEMM，GEMM 占 80%、Attention 占 10%；场景 B 里 Attention 涨到 40%，GEMM 降到 50%。

现在同样把一类算子的耗时降低 30%。场景 A 里优化 Attention，整步只降 3%；优化 GEMM 降 24%——同样的算子提速幅度，对整步的贡献差了八倍。换到场景 B，两者变成 12% 和 15%，差距几乎没有了。

右边三条是为什么要回到模型看收益。第一，占比决定直接收益，占比小的算子再快也带不动整步。第二，整步耗时还不是服务容量，排队、批次、缓存和时延目标都会改变最终结果。第三，每轮优化之后瓶颈可能转移，下一轮要按新的 Trace 重排优先级。

结论就是最下面这句：先按负载判断优化优先级，再用整模型压测确认最终收益。

**被问到再说**

- 四个数都是按占比直接换算：整步降幅等于该算子占比乘以提速幅度。场景 A 的 GEMM 是 80% × 30% = 24%，Attention 是 10% × 30% = 3%。
- 这里只算了单步耗时。真实服务里 TTFT 包含排队，提速会被放大；而 decode 阶段受显存带宽约束，提速可能被吃掉。所以最终仍要压测。
- 占比本身随输入形状变化：长上下文下 attention 的占比会显著上升，所以优先级要按目标负载重新算，不能套用别的场景的结论。

## 8 / 8　算子耗时到服务容量

*约 105 秒（1:45）*

最后一页讲方法：从算子耗时一路算到单机容量，这条链怎么用。

五层从左到右，越往右越接近业务指标，也越依赖实测校准。算子耗时取计算时间和访存时间的较大者，再加启动与通信开销；单步耗时按真实 batch 形状汇总，区分 prefill 和 decode；请求时延要模拟请求与批次、考虑缓存准入；再按业务目标判断 TTFT、TPOT 的达标率，看哪个环节先超标；最后搜索满足 SLO 的最大请求到达率，也就是单机容量。

下面这条回环是关键：用服务日志与压测校准预测偏差，再重新选择优化方向。没有校准，这条链只能排序，不能报数。

Agent 目前怎么用它，三件事进度不同，页面上如实标注了。定位热点已经接入，按真实 Trace 找热点、在固定负载上验证候选。What-if 推演等 M100 校准，校准之后用来筛选优化方向。向算子层提需求这条还待补齐，要形成 shape 与实现需求，新内核回接后再做模型复验。

一句话收尾：这条链只用于排优先级；任何进入交付的收益，都以整模型实测为准。

**被问到再说**

- 这条链目前的预测偏差还没有在 M100 上标定，所以 What-if 那一格标的是待校准。在标定之前，它只用来比较候选的相对优劣，不对外报绝对数字。
- 容量定义是满足 SLO 的最大请求到达率，依赖具体的 TTFT / TPOT 目标；换一组业务目标，排序可能变化。
